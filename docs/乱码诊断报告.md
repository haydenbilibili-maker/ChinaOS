| 集中文件 | **全部在 `china.html`**（其它 23 个 HTML 干净） |

## 二、根因：编码写入端的「字符丢失」，**不可逆**

抓取实际字节确认，乱码是连续的 `3f 3f 3f...`（字面 `?`），而**没有任何 `�`**。
这两点合起来指向一个明确结论：

- 不是「显示乱码 / 浏览器字符集设错」——文件本身是合法 UTF-8（`file -I` 确认）。
- 不是「GBK 被当 UTF-8 解码」——那种情况会留下 `�` 或高位串字，这里一个都没有。
- **真正发生的是：某一次写入时，内容流经了一个无法表示中文的编码器**
  （如 ASCII / Latin-1 / cp1252，配合 `errors="replace"`），
  每个中文字符被替换成了字面 `?`。**原始汉字在那一刻已被销毁。**

### 重要推论
- 这些内容**无法靠「重新转码 / 改 charset」找回**——字节已经没了。
- 受损 Tab 的文案必须**依据《中国深度调研系列》索引重新撰写**，而非修复编码。
- 仓库内历史脚本 `scripts/china_html_mojibake_batch.py` 读写均为 `encoding="utf-8"`，
  **不是元凶**；丢失发生在更上游（编辑器/外部工具/粘贴管线某次以非 UTF-8 存盘）。

## 四、修复策略建议

1. **止损（已完成）**：装 pre-commit 门禁（见下），从此**不再新增**乱码。
2. **分批重写**：按上表从高命中函数起，逐个 Tab 依索引文案重写——
   每修一个 Tab 提交一次，借助 Git diff 可精确验证「只增不损」。
3. **优先级**：H2 可见区（605 行）优先于 H3 注释（86 行）；
   注释里的 `?`（如 `dataBus.on(...)` 内）可顺手清理或直接删注释。
4. **根因封堵**：统一编辑工具链强制 UTF-8 存盘；禁止任何脚本以
   非 UTF-8 编码 `write_text`。

## 五、门禁用法
