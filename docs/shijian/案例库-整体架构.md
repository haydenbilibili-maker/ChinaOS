## 1. 案例库的定位

案例库不是史料的堆叠，而是**史鉴引擎（SJ-02 四步法）的证据层**：每个案例都是"结构切片→周期定位→机制归因→古今映射"在一个真实历史时点上的一次完整运行，产物是可比、可累积、可外推的史鉴台账。案例越多，越要靠**综合层**把它们收束回母本的八条规律（第四部）——否则只是散点。

三层结构：

```
综合层（synthesis）   ← 跨案对比矩阵：把同类案例收束成规律（SJ-07 已有崩解一张）
   ▲
案例层（cases）        ← 单案台账：每案一张七字段史鉴台账（SJ-05/06/08–15…）
   ▲
真源层（bible）        ← 案例核心母本：每案的 seed 内容 + 史料 + 核验状态（本轮补建）
```

## 3. 双范式判据（台账 vs 对比矩阵）

案例库有且仅有两种产出形态，判据必须显式：

- **单案台账（`sj-ledger-*`）**：当焦点是**一个时点/一场改革/一次崩解的机制深描**时用。七字段固定顺序。SJ-05/06/08–15 属此。
- **跨案对比矩阵（SJ-07 式）**：当焦点是**多案共性/差异的规律提炼**时用。行=案例、列=五力（或其他维度），单元格编码角色（引燃/共振/次要）。SJ-07 崩解矩阵属此。

**判据一句话**：讲清"这一个案例怎么运转"→台账；回答"这一类案例的规律是什么"→矩阵。二者互补，不可混用于同一模块。

## 4. 综合层规划（Synthesis）—— 案例库的"结论产品"

每个**案例类型**满 3 案后，须建一张跨案对比矩阵，把散点收束成规律。这是案例库最高价值的输出。

| 综合矩阵 | 覆盖类型 | 状态 | 列维度建议 |
|---|---|---|---|
| **崩解归因矩阵** | bengjie | ✅ SJ-07 | 五力（引燃/共振/次要）+ 崩解形态 |
| **变法谱系矩阵** | bianfa | ✅ SJ-16（成员：SJ-05/09/11/13/14） | 汲取工具 / 触动的力 / 皇权依赖度 / 成败 / 存续 |
| **上升奠基矩阵** | shangsheng | ✅ SJ-17（成员：SJ-27/34/35/38） | 五力协同项 / 制度模块 / 可持续性 |
| **拐点谱系矩阵** | guaidian | 规划 SJ-18〔预留〕（成员：SJ-06/49 + …） | 主导力 / 强化的单力 / 隐性程度 / 崩解距离 |
| **分裂—重整矩阵** | fenzheng | 规划 SJ-19〔预留〕（成员：SJ-08/31 + …） | 畸大之力 / 合法性归零度 / 再统一路径 / 过度矫正 |

**规则**：综合矩阵引用其成员单案台账为史料源（交叉链接），不重复深描；矩阵的每条结论须映射回母本第四部某条规律（编号引用）。

## 5. 案例深度分层（Depth Tiers）+ 质量门

废止"每案都追求深描"的隐性预期，代之以显式三层。**每案在母本中标注其 Tier**；执行侧据此配置分量，避免 SJ-15（19KB）式的参差被误读为缺陷或过度。

| Tier | 定位 | 分量 | 台账要求 | 史料核验 |
|---|---|---|---|---|
| **T1 深描** | 范式验证案 / 母本样板案 | 40KB+ | 七字段全展开；五力归因双列每力有实因；史家交锋 5 家 | 关键引证逐条 WebSearch |
| **T2 标准** | 主线案例（多数） | 28–36KB | 七字段齐全；五力归因≥3 力有实因；史家交锋≥4 家 | 关键纪年/人物/著作核验 |
| **T3 索引条目** | 补全 / 次要案例 | 轻量卡片 | 拐点 + 相位 + 主导力 + 一句古今映射；不强制完整交互切片 | 纪年核验 |

**质量门（交付前硬检查）**：
1. 该案在《案例库-核心母本》有 seed 条目（母本先行，见规则）。
2. 台账字段符合其 Tier 要求；`未决` 列非空或显式标"无重大未决"。
3. 每处古今映射有"关键差异"栏（禁裸类比）。
4. 每个纪年/关键人物/著作有出处或〔存疑〕；T1/T2 的关键引证已 WebSearch 核验并去〔存疑〕。
5. 自足/marker 无悬挂/节点 id 与 JS 键对齐/标签平衡/a11y（沿用既有校验）。

## 6. 数据契约（Case Object）

每个案例是一个统一对象，驱动 Hub filter、综合层聚合、卷目导航。母本、registry、Hub 卡片三处的字段必须一致。

```
{
  sj: "SJ-11",
  朝代: "chunqiu",              // 轴一 dynastyId
  类型: "bianfa",               // 轴二 typeId
  标题: "商鞅变法",
  一句话拐点: "...",
  相位: "上升→僵化",            // 对接 SJ-04
  主导力: ["fiscal","elite"],   // 对接 SJ-03 五力 id
  tier: "T2",
  史料: ["《史记·商君列传》","《商君书》"],
  核验状态: "待核验",           // 待核验 / 已核验 / 存疑
  映射种子: "军功爵通道 → 当代绩效晋升..."
}
```

Hub 卡片 `data-dynasty` + 新增 `data-type` 双 filter；综合矩阵按 `类型` 聚合成员。

## 7. 扩张治理（Governance）

沿用路线图 Round 分批，但叠加两条策略性约束：

1. **深度优先于广度（本阶段）**：Round 1 已把广度铺到 11 案但深度欠账。**下一阶段先补债，再扩张**——即先为 SJ-09~15 补母本 seed + 核验 + 补齐到 T2，再建 Round 2 新案。
2. **每 Round 收一张综合矩阵**：新案落盘的同时，推进一张综合层矩阵（如 Round 2 交"变法谱系矩阵"，因变法案已够 5 个）。让案例库每一轮都产出"规律"，而不只是"更多案例"。

Round 优先级（修订）：
- **Round 1.5（补债）**：SJ-09~15 母本 seed + 核验 + T2 补齐；**变法谱系矩阵**（新综合卷）。
- **Round 2**：文景/隋文帝/贞观/两税法/靖康/康乾（路线图原案）+ **拐点谱系矩阵**。
- **Round 3+**：按路线图。

## 9. 持续开发规则（案例库专项，摘要；完整版见 .cursor 规则增补）

1. **母本先行**：任何案例 HTML 落盘前，该案必须先在《案例库-核心母本》有 seed 条目（拐点/相位/主导力/史料/核验状态/映射种子）。禁止从"标题 + 一句话"直接产 HTML。
2. **双轴归档**：每案标注朝代 + 类型；台账重心随类型调整。
3. **范式判据**：机制深描→台账；规律提炼→矩阵；不混用。
4. **深度分层**：每案标 Tier；按 Tier 配分量、配核验强度；不追求"案案深描"。
5. **核验协议**：T1/T2 的关键纪年、人物、著作、制度名逐条 WebSearch；去〔存疑〕或保留并说明。
6. **综合先于扩张**：某类型满 3 案即收综合矩阵，再扩新案。
7. **禁裸类比**：映射字段"相似机制 + 关键差异"成对，缺一不成立。
8. **视觉与自足**：沿用暖色 `--sj-*` 皮肤、双栏 `sj-page-layout` 布局、卷轴+朱批母题、自足单文件、a11y（reduced-motion/focus-visible/tabindex/role）。
